**Both Azure OpenAI widgets on the Model Backend Health dashboard were rendering empty, in all 25 orgs.** They queried `service:api env:production "Too Many Requests"` and `service:api env:production "Stream aborted mid-flight"`; measured against the live gsa logs API, **both return zero events over 30 days**, so both graphs had been blank for however long the service topology has been as it is. Two independent faults, both found by probing rather than reasoning. **(1) Wrong service scope.** Azure OpenAI work is split across *two* services now, `api` and `api-beta`, and the throttle signal appears under **both** — measured over 14 days in gsa: `api` = 2801, `api-beta` = 2609, and 5410 via `service:(api OR api-beta)`. Neither service alone captures it, so the `OR` form is not defensive padding, it is required for a correct count. **(2) Wrong phrase.** The log text is not "Too Many Requests" — that string appears only in `cloudtrail` logs in these orgs, which is why a bare search for it looked like it matched something. Azure's actual wording is e.g. `Your requests to gpt-5.5 for gpt-5.5-latest-guardrails-defaultv2 in eastus2 have exceeded rate limit.`, so the correct match is `"exceeded rate limit"` — **4509 events in gsa over 7 days**, happening constantly with nothing displaying it. The "Stream aborted mid-flight" widget was worse: that phrase returns 0 across **all** services and all of `env:production` over 30 days, and so do `"stream aborted"`, `"aborted mid-flight"` and bare `"abort"`. The signal it was built for (the 2026-06-02 incident) no longer exists in the logs at all, so repointing it at a variant would only have produced a differently-empty graph; it is repurposed to the upstream-500 signal that **does** exist (78 events/7d in gsa, e.g. `500: Internal Server Error | headers: {...'Server': 'envoy'...}`), which is the closest real measure of Azure-side failures reaching users. Widget titles now name both services so the scope is visible on the dashboard rather than hidden in the query. **The same two broken queries were also live in `main.tf`'s two Azure monitors**, where `on_missing_data = "default"` has kept them permanently `OK` while matching nothing — a silent-monitor bug of exactly the kind `cert_monitors.tf` documents for `synthetics.ssl.days_left`, and the reason Azure throttling has never once alerted despite 4509 events in a week. Correcting those queries while keeping `> 3 in 5m` would page roughly **19×/day per org, ~480/day across 25 orgs**: the measured 5m-bucket distribution in gsa over 7d is throttling present in 12.1% of windows, median 4, p95 76, p99 206, max 240 — i.e. throttling is a normal operating condition here, not an incident. And a count threshold cannot work fleet-wide at all, because 7d totals are gsa 4509, doc 323, ftc 15, dot 5, hud 0 — a ~900× spread, where a threshold quiet enough for gsa would never fire for dot even during a total outage. That is precisely what the `CLAUDE.md` "prefer RATES over absolute counts across tenants with different traffic" convention exists for, and the shape that produced the ~200-alert flood in PR #42. So the monitor queries are corrected but the *threshold* redesign (ratio vs sustained-duration vs per-tenant variable) remains an open decision — handled as described below rather than silently half-applied.

**Both Azure monitors are fixed too, with deliberately different treatments.** `azure_openai_throttling` gets the corrected query but is made **fully handle-less** — zero notification channels — because its `critical = 3 / warning = 1` thresholds were calibrated in 2026-06 against a query that matched nothing and have never met real data. Now that the query works, `> 3 in 5m` is breached ~19×/day in gsa alone, and the ~900× cross-tenant spread means no count value can serve both gsa and dot. It therefore evaluates and displays the truth on its own page and on the dashboard while sending nothing, and the retune (ratio vs sustained-duration vs per-tenant variable) is left as an explicit open decision with the measurements recorded in-file. Its name carries `(no page - threshold un-tuned)` and its alert body states plainly that a breach is not by itself an incident, so nobody mistakes the signal for a call to action. The in-file note also carries the honest caveat learned in PR #48: handle-less monitors get ignored — the 45-day cert tier was handle-less on identical "it's a ticket, not a page" reasoning and ed/gsa still reached 18 days to expiry unseen — so this is flagged as a short-lived interim rather than a resting state. `azure_openai_stream_aborted` is **repointed** to the upstream-500 signal and **keeps its handle**, because that signal measured out safe: over 7 days in 5m buckets, gsa has 80 events (non-zero in 48/2016 windows, max 6, p95 3) so `> 3` fires twice a week, usda once, hud never, and doc/ftc/dot have none — roughly 0.3 pages/day in the busiest org, with no 900× spread to defeat a count threshold. It is renamed `Azure OpenAI - upstream 500s reaching the app` and its body records that the old mid-stream-cutoff symptom is no longer instrumented anywhere, so the 500 count is explicitly a proxy rather than a rename of the same thing. Handle placement verified programmatically after the edit: throttling has 0 handles, aborts has 2 (`{{#is_alert}}` + `{{#is_alert_recovery}}`, never bare `{{#is_recovery}}`, with a handle-less warn tier) per the PR #22 convention.
