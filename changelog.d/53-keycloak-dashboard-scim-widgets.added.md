**SCIM provisioning section on the aigov Keycloak dashboard** (7 widgets: a section note, three counters, two timeseries and a raw log stream), because nothing on any dashboard or monitor showed SCIM provisioning health and a fleet-wide breakage consequently ran unnoticed from 2026-08-25 to 2026-09-09. The trigger was an ED access report: users could not get into USAi, and every `GET /realms/ed/scim/v2/Users` from Entra was returning **401**. Keycloak itself was healthy the whole time — a freshly minted client-credentials token returns `200` and a valid SCIM `ListResponse` on `ServiceProviderConfig`, `Users` (2,431), `Groups`, `Schemas` and `ResourceTypes` — so the failure was entirely a stale IdP credential, invisible because nothing watched for it. Widgets show 401s vs successes from real IdP traffic, request volume over time by status, a per-realm 401 breakdown across the eight realms that have a `scim-client` (`ed ntsb faa doj ncua doc sss opm`), and the raw log stream for triage. **Three properties of these logs shaped every query and are documented in the section note rather than left to be rediscovered.** (1) They are **istio-ingressgateway access logs**, not `service:keycloak` events, so realm and HTTP status live in raw message text with **no parsed attributes** — `@http.status_code:401` returns zero. Status is therefore matched as a text term, verified against 30 days of real data (`"scim/v2" 401` returns 54 hits that are *all* genuinely 401, no over-matching from byte counts or durations, which is a real hazard in envoy access logs and did bite an earlier `429` query elsewhere). (2) **None of the dashboard's template variables apply** — `$realm`, `$event_type` and `$environment` resolve to `@realmName`, `@type` and `env`, and all three return **zero** against these logs, so adding any of them silently blanks the whole section. The note says so explicitly and a scripted assertion rejects any SCIM query containing `$`. (3) The logs are level **`info`**, not `error`, so no error-severity filter or monitor would ever have surfaced them — the direct cause of the two-week blind spot. Queries also carry `-curl` to exclude manual probing, which matters more than it looks: without it the picture reads `401: 54, 200: 20` and looks partly healthy, when in fact **every one of those 200s is hand-run `curl`** — four from setup testing on 08-25 and the rest from this investigation — and `"scim/v2" 200 -curl` is **0**, meaning SCIM has never once succeeded from an actual IdP in 30 days. Plan: 1 dashboard updated, 0 added, 0 destroyed. The update also drops a `notify_list` key that is `null` live, so no recipients are affected.
