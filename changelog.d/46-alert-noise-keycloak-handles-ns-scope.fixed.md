Cut ~18 of ~56 daily alert emails by fixing two noise sources measured from a full day of `usai-tenant-operations` traffic (2026-08-19: 56 emails in 10.5 hours, of which 71% were conditions that either could not be fixed from this repo or should never have paged). **(1) The bare-notification-handle bug, again — this time in the root module.** All five shared-Keycloak monitors in `monitors.tf` carried `${var.notification_channel}` as a trailing line outside every conditional block, so Datadog rendered the handle on Warn, on Recovered *and* on Triggered. A 4-minute transient login-error spike at 10:06 therefore produced **six** emails (Warn, Warn, Recovered, Warn, Recovered, Recovered) from two monitors. This is the identical bug PR #22 removed from the per-tenant monitors and the reason `CLAUDE.md` carries the "scope the handle to `{{#is_alert}}`" rule; these five were missed because they live in the **root** module (aigov-only) rather than `modules/model_backend_monitors`, so the PR #22 sweep never reached them — the convention applies to the root module too, and the file header now says so. Handles are now scoped to `{{#is_alert}}` / `{{#is_alert_recovery}}`, warn tiers are deliberately handle-less with an explanatory body, and recovery uses `{{#is_alert_recovery}}` rather than bare `{{#is_recovery}}` (with a warn tier set, bare still pages on WARN→OK). **(2) `deployment_unavailable` was scoped `{*}`**, so it watched every deployment in the cluster rather than the USAI application. A 2026-07 Calico upgrade added `goldmane` and `whisker` to `calico-system` on eeoc; both sat unready and the monitor re-paged every 2h for **28 days** — 12 emails/day about platform add-ons that are neither USAI nor on-call's to fix. Now scoped to a new `var.app_namespaces` allowlist (`core-api`, `core-chat`, `core-console`, `chat-beta`, `api-beta`), verified against live kube-state-metrics to return exactly the 9 application deployments; the other nine in-cluster namespaces are all platform. An **allowlist, not a blocklist**, deliberately: a blocklist fails open, which is precisely how goldmane/whisker slipped in, whereas an allowlist ignores new platform namespaces by default. The trade-off is explicit — a new USAI namespace must be added to the variable or it goes unmonitored — and nothing critical is lost, since a broken `istio-ingressgateway` surfaces via the edge synthetics and a broken `datadog-cluster-agent` via the agent-telemetry monitor. The `IN (...)` filter syntax was verified against the live gov query API before commit rather than assumed. Also adds `lifecycle { ignore_changes = [assets] }` to the five Keycloak monitors: `assets` is an optional block on `datadog_monitor`, so with none declared Terraform sends an empty list and **deletes** the runbook notebooks operators attached in the UI — a plan on 2026-08-18 showed exactly that (`assets: [{runbook /notebook/20715...}] → []`) on all five. Runbooks are real operator work and aren't modelled here, so they're ignored rather than clobbered. Documents, without changing, a **known redundancy**: `keycloak_login_failures_spike` (>20), `keycloak_login_success_rate_drop` (>40) and `keycloak_top_failing_clients_spike` (>15) run the *identical* query — a 5m rollup count of `type=LOGIN_ERROR env:production` — at three thresholds, so one spike can page up to three times (both >20 and >15 fired at 10:06). Two are also misnamed for what they measure: "success rate drop" computes no rate, and "top failing clients" has no `by {client}` grouping. Collapsing them changes *what* is alerted on — a monitoring-design decision, not a noise fix — so it is left for its own PR, with in-message NOTEs telling whoever gets paged what each monitor actually measures. Plan: 30 in-place updates (25 `deployment_unavailable` + 5 Keycloak), 0 created, 0 destroyed, runbook assets confirmed unchanged.
