**`pod_restart_storm` no longer asserts a cause it never checked, and no longer fans out to one page per deployment.** The monitor was named `...(deployment cycling pods, image unchanged)` and its body stated *"This is a restart STORM, not a deploy: check whether the image tag is actually changing"*. **The query has never looked at the image** — it measures only `avg pod age < 90m over 4h`, which proves pods are being replaced faster than they can age and says nothing about why. So the confident claim was simply false whenever the cause was deploys, and it actively misdirected triage toward external-secrets and HPA metrics. It misfired exactly that way on 2026-08-20: **214 alerting groups across 23 of 25 orgs** (every deployed tenant, all 9 app deployments each), every one asserting "image unchanged". The real cause was **20 reconcile-triggering commits to the shared Flux mono-repo `mcaas-gsai/gsai-flux-mono` between 15:34Z and 19:27Z** — including five `Automated image update` commits, so the images demonstrably *were* changing — with the first (PR #411) touching `base/apps/console-pipeline/helmrelease.yaml`, which every tenant inherits, so one `base/` change rolled the entire fleet. Roughly one reconcile every 12 minutes matched the measured pod-age reset cadence (`36m → 6m → 2m → 19m…`) exactly. Alternatives were ruled out by measurement and the list is now preserved in-file as the discriminator set: metric artifact (kube-state-metrics and cluster-agent restarts both 0; `pod.age` continuous, 179 points, 0 nulls), node churn (node counts flat all day), HPA thrash (every HPA pinned at its minimum, zero oscillation), and crash loop (app container restart counts **flat, delta 0** — pods were being *replaced*, not restarted). The name is now `Pods cycling — deployments not staying up (deploy storm or restart loop)` and the body states what the query measures, explicitly says it does not identify the cause, then hands over a four-step decision procedure ordered cheapest-first: check the Flux mono-repo for a commit burst (especially `base/`) since fleet-wide lockstep churn across 25 independent clusters is almost never a fault; then `kubernetes_state.container.restarts` climbing vs flat as a **verified** discriminator between crashing and being replaced; then the external-secrets/reloader loop that was the 2026-07-22 cause; then HPA oscillation. It also records what is **not** usable despite seeming obvious: there is no per-deployment ReplicaSet count in this data, because `kubernetes_state.replicaset.replicas_desired` carries no `kube_deployment` tag, so the old runbook's "count the ReplicaSets on the same image" returns **no series** — verified, and replaced with the `kubectl get rs --sort-by=.metadata.creationTimestamp` equivalent. **The monitor still pages, deliberately**: `replicas_ready` on ftc's chat dipped to **1 of 8** during the churn and `deployment_unavailable` did *not* fire because the dips averaged out over its 30m window, making this the only monitor that caught a genuine availability degradation — so demoting it to a handle-less warn tier would have lost real signal. Fan-out is fixed instead, with `notify_by = ["kube_cluster_name"]`: notifications collapse to one per cluster while group **evaluation** stays per-deployment, so the monitor page still shows exactly which deployments are affected but a whole-cluster event sends one page rather than nine (**214 → 23**), on the reasoning that a whole-cluster churn event is one incident. This is also why the body no longer uses `{{kube_deployment.name}}` — with notifications aggregated above the deployment level, a per-deployment template would render one arbitrary group's name and read as though it were the only one affected. `renotify_interval` also drops from 120 to **1440**, matching `cronjob_failing` (PR #39) and the cert monitors, since a persistent churn condition re-notified 12× a day carries no new information. Combined effect: ~214 pages every 2h becomes ~23 per day. Plan: 25 in-place updates, **query unchanged** so no group state is reset and currently-alerting groups keep their history.
