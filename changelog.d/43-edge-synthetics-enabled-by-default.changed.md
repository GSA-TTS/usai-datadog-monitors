**Edge synthetics are now enabled by default** (`enable_edge_synthetics` false → true, `synthetic_locations` `[]` → `["aws:us-gov-west-1"]`), retracting the WAF caveat that gated the whole feature off. The header of `cert_monitors.tf` carried a "LOAD-BEARING CAVEAT" asserting that Datadog's public locations egress from IPs outside the edge WAF's default-BLOCK + GSA/Zscaler allowlist, so a public-location test "would be BLOCKED by the WAF and fail forever" and `enable_edge_synthetics` had to stay `false` until a private location was provisioned. That claim is **disproven by live evidence** (2026-08-18): 16 hand-built UI synthetics have been running from the *public* `aws:us-gov-west-1` location across these same tenant orgs since 2026-04, and 15 of them sat in `OK` — they went red only when the tenant hostnames moved to the apex, never because of the WAF. The original conclusion came from PR #40's test-apply against **eeoc**, where a public-location synthetic timed out and that timeout was read as a perimeter block; the more likely reading is that eeoc's edge was genuinely not serving at the time — a missing production certificate was the entire subject of the 2026-08-04 EEOC incident — so the test failed for the reason being investigated, and "the WAF blocks Datadog" was generalized from a *client* on a non-allowlisted network into a claim about Datadog's egress that nobody probed independently. Cost of the error: roughly four months with the edge unmonitored in Terraform while unmanaged UI tests did the job badly. A private location still works if one is ever provisioned; it is simply not required. Also binds the synthetics' timing to new shared locals (`edge_synthetic_tick_s`, `edge_synthetic_min_failure_s`, `edge_synthetic_renotify_min`) per the #33 no-drift rule, since the same values appear in every test's `options_list` and are quoted in the alert bodies. Two tenants are explicitly opted **out** in `tenants.tf` rather than monitored with tests that can only fail: **doli** (no working public edge at all — `dol.usai.gov` does not resolve, and every path on `chat.dol`/`console.dol` returns `404`) and **ang** (app not deployed — `ang.usai.gov/healthz` returns a genuine `503` with `chat.`/`console.ang` not connecting, while in the ang org the Deployment-availability, Pod-restart-storm and all three Bedrock monitors read `No Data` against `OK` EC2/RDS, i.e. infrastructure without workload). Both are documented as deliberate monitoring gaps with the condition for flipping them back on, on the reasoning that a permanently-red monitor teaches people to ignore it — ang's pre-existing UI synthetic had been sitting in `Alert` on exactly this.
