**`deployment_unavailable` notifications are deduplicated to one per cluster** (`notify_by = ["kube_cluster_name"]`), closing the same latent fan-out that `pod_restart_storm` was hit by in #49. Grouping by cluster/namespace/deployment is correct for precision — you need to know *which* deployment is short of replicas, and one bad deployment must not mask another — but it means a fleet-wide cause emits one notification per deployment per org. That is exactly what happened to the pods-cycling monitor on 2026-08-20: **214 pages across 23 orgs from a single Flux commit burst**. This monitor has the identical grouping shape and had simply not yet been hit by a fleet-wide availability event; today's incident showed it is a matter of timing rather than design. `notify_by` aggregates **notification** to one per cluster while leaving group **evaluation** per-deployment, so the monitor page still names every affected deployment and namespace, but a whole-cluster event pages once instead of nine times. The alert body is rewritten accordingly and no longer uses `{{kube_deployment.name}}` / `{{kube_namespace.name}}` as its subject: with notifications aggregated above the deployment level those templates render one arbitrary group and read as though it were the only deployment affected, which is more misleading than directing the reader to the monitor page. The new body states plainly that **users are affected right now** (missing replicas is capacity loss, not a warning about future risk), keeps the existing cause list and `kubectl` triage, and adds a fleet-wide hint: if this fires across many tenants at once, suspect a rollout rather than 23 independent faults — check `mcaas-gsai/gsai-flux-mono` for a commit burst, especially anything touching `base/`, which every tenant inherits, and cross-check the pods-cycling monitor, since sustained churn there plus unavailability here is a deploy storm degrading capacity. **`renotify_interval` deliberately stays at 120**, unlike `pod_restart_storm` and the cert monitors which moved to 1440: those describe conditions that are bad but not actively costing capacity, whereas this one means replicas are missing right now and a stuck rollout nobody notices for a day is a real outage — consistency with sibling monitors is not a reason to slow it down. The bare `{{#is_recovery}}` block is retained and remains correct: this monitor has only a `critical` threshold and no warn tier, which is the documented exception in `CLAUDE.md` (a handle-less warn tier is what makes bare `is_recovery` dangerous, and there isn't one here). Plan: 25 in-place updates, with query and monitor name unchanged so no group state is reset and no alert history is lost.
